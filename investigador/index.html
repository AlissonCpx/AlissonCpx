Monte o seu investigador

O prompt abaixo guia qualquer CLI de IA a montar, na sua máquina e com as suas ferramentas, o mesmo desenho que eu apresentei. Ele pergunta o seu stack antes de escrever qualquer coisa.

Antes de colar

Três coisas que valem trinta segundos de leitura e evitam meia hora de frustração.

  • Você precisa de um CLI de IA instalado — Claude Code, Devin, Codex, Cursor CLI, qualquer um que rode no terminal. É o único requisito real.
  • Rode dentro de uma pasta vazia dedicada. O prompt vai criar arquivos ali.
  • Ele vai fazer perguntas antes de escrever. Responda com o que você usa de verdade, não com o que seria ideal.

O prompt

Copie inteiro e cole no seu CLI.

Prompt de setup 
Você vai me ajudar a montar um investigador automático de alertas e bugs: um agente que roda sozinho de tempos em tempos, investiga o que apareceu e me entrega a análise pronta para quando eu pegar a tarefa.

Antes de escrever qualquer arquivo, me faça as perguntas abaixo UMA POR VEZ, esperando minha resposta antes de seguir para a próxima. Se eu não souber alguma, sugira a opção mais comum e siga.

1. Que ferramenta de observabilidade e alertas meu time usa? (SigNoz, Grafana, Datadog, New Relic, Sentry, CloudWatch, Prometheus/Alertmanager, outra)
2. Onde ficam os bugs e tarefas? (Jira, Linear, GitHub Issues, Azure DevOps, outra)
3. Onde fica o código? (GitHub, GitLab, Bitbucket, outro)
4. Onde ficam os logs? (Kibana/Elasticsearch, Datadog Logs, Loki, CloudWatch Logs, outro)
5. Onde o time conversa e quer receber o resultado? (Slack, Teams, Discord, ou só um comentário na própria tarefa)
6. Que CLI de IA eu tenho instalado aqui? (Claude Code, Devin, Codex, Cursor CLI, Gemini CLI, outro)
7. Como o meu time identifica o que é dele nessas ferramentas? (label, campo customizado, projeto, prefixo de serviço)
8. Que serviços ou repositórios esse time mantém?

DEPOIS DE PERGUNTAR TUDO, faça nesta ordem:

PASSO A — Descubra o que dá para conectar.
Para cada ferramenta que eu citei, verifique se existe MCP server oficial ou comunitário e como configurá-lo. Onde não existir, confira se a ferramenta tem API REST e prefira curl direto. Me mostre o que encontrou e o que vai usar em cada caso ANTES de escrever código.

PASSO B — Monte quatro peças, nesta ordem.

1) O PORTEIRO — um script shell que:
   - faz UMA chamada HTTP barata para perguntar "tem trabalho novo?"
   - se não tem, encerra com exit 0 sem acionar a IA
   - se tem, compara com um arquivo de controle de itens já investigados (uma linha por item: identificador e data, janela de 7 dias)
   - só então chama o CLI de IA, já passando a lista filtrada
   - registra os itens no arquivo de controle ao terminar
   Esta é a peça mais importante. Em dia calmo o custo tem que ser zero, porque o modelo nem chega a ser acionado.

2) O RUNBOOK — um arquivo markdown com o passo a passo que um desenvolvedor sênior seguiria: coletar o item, buscar os logs, ler o código, decidir, agir, notificar, registrar. Inclua uma tabela com os serviços do time e uma seção de regras no final. Escreva como briefing para uma pessoa, não como fluxograma.

3) O GATE — dentro do runbook, a regra de quando ele pode propor correção. Todos os critérios precisam ser verdadeiros:
   - causa raiz identificada com certeza, não palpite
   - alteração de no máximo 30 linhas
   - não altera contrato público (API, modelo de dados)
   - não exige decisão de arquitetura
   E sempre como rascunho/Draft, nunca merge automático, nunca push em branch protegida.
   O limite de 30 linhas NÃO é por segurança. É o tamanho em que dá para revisar batendo o olho. Se for maior, eu teria que parar tudo para revisar, e o ganho de tempo desaparece.

4) A ENTREGA — o resultado precisa chegar onde o time já olha: comentário na própria tarefa ou mensagem no canal. Nunca um arquivo que ninguém abre.

PASSO C — Me dê a linha de cron para rodar de hora em hora em horário comercial, e me explique como testar cada peça isoladamente antes de agendar.

REGRAS QUE VALEM PARA TUDO:
- Nenhum segredo dentro de arquivo versionado. Use variáveis de ambiente e me diga como carregá-las no cron.
- O objetivo não é abrir correção. É me entregar a análise pronta. Correção é bônus, e só quando for barata de aceitar.
- Comece pelo caso mais simples que funciona. Se der para cortar uma peça, corte.
- Ao final, me diga em uma frase qual é a primeira coisa que eu devo rodar à mão para ver se está de pé.
O que esperar

Ele vai fazer oito perguntas, pesquisar as integrações do seu stack, e sair com três arquivos: um script, um markdown e um arquivo de controle. Mais a linha do cron.

Se o resultado parecer complicado demais, ele errou o espírito. Peça para simplificar — a versão certa cabe em uma manhã.

Os quatro princípios, se você quiser montar do zero

O prompt é atalho. O que importa mesmo são estas quatro ideias, e elas independem de ferramenta.

01

Porteiro antes do modelo

Uma checagem grátis decide se vale acordar a IA. O curl é de graça, o token não é. É isso que torna "de hora em hora" viável.

02

Runbook, não fluxograma

Escreva o que um sênior faria, em markdown. O modelo decide o caminho; o texto só dá a direção e os limites.

03

Correção barata de aceitar

Trinta linhas é o tamanho em que revisar não custa nada. Acima disso você volta a gastar o tempo que queria economizar.

04

Entregue onde o time olha

Comentário na tarefa, mensagem no canal. Relatório em pasta é trabalho que ninguém lê.
